# 🗺️ Blueprint: AI-driven SDLC с импортозамещением

**Статус:** Production-Ready. Готов к промышленному внедрению в enterprise-контуре с требованиями импортозамещения, 152-ФЗ и жёсткого контроля затрат.

**Версия:** 1.1 (добавлены Enforceable-звенья, Guide Right, защита от парадокса Джевонса)

* * *

## 📖 О документе

Этот Blueprint описывает **корпоративный стандарт разработки с AI-усилением**. Он не является «набором промптов» или «идеалистической схемой». Это операционная система для AI-driven SDLC, которая:

  * Считает деньги (Compute Units, Cost per Task, TCO).
  * Контролирует latency (фоновые vs интерактивные агенты).
  * Защищает данные (Secret Scanning до LLM, NER-маскирование, on-premise).
  * Управляет изменениями (Fast-Track, Hotfix, обратные связи).
  * **Делает отклонение от архитектуры физически невозможным, а не просто обнаружимым** (Enforceable-звенья).
  * **Управляет генерацией в реальном времени** (Guide Right).
  * **Защищён от парадокса Джевонса** — метрика «сколько фич мы решили НЕ делать».
  * Улучшается с каждым ревью (Context Enrichment).

## 🔄 2. Конвейер: этапы, артефакты, контроль

### 2.1. Схема конвейера

    +----------+   +----------+   +----------+   +----------+   +----------+
    | PROPOSAL |-->|  SPECS   |-->|  DESIGN  |-->|   ADR    |-->|   API    |
    +----------+   +----------+   +----------+   +----------+   +----------+

                                                                        v
    +----------+   +----------+   +----------+   +----------+   +----------+
    |  APPLY   |<--|  TASKS   |<--|   ...    |<--|   ...    |<--| CONTRACT |
    +----------+   +----------+   +----------+   +----------+   +----------+

    ОБРАТНЫЕ СВЯЗИ: Change Request | blocked-by | supersedes

### 2.2. Этап 1: Proposal → Specs

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra (фоновый), промпт «анализ идеи → specs»  
**Контекст** | Бизнес-ограничения, интеграции, история похожих фич  
**Артефакт в Git** | `docs/specs/feature-X.md`  
**Точка контроля** | Аналитик проверяет черновик, дополняет контекстом  
**Обратный ход** | Если specs неполны → новый коммит, уведомление аналитика  
**Latency-класс** | Фоновый  

**Правило:** specs — источник истины для всех последующих этапов. Изменение specs после принятия ADR требует нового RFC.

**Enforceable:** каждая спецификация обязана содержать секцию Acceptance Criteria в формате Given/When/Then. Без неё PR с specs блокируется Gitea Actions. Эти критерии становятся acceptance-тестами на этапе Apply (§14).

### 2.3. Этап 2: Specs → Design + ADR

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra, навык генерации ADR (шаблон MADR)  
**Контекст** | Specs + текущая архитектура (из Context Provider)  
**Артефакт в Git** | `docs/design/feature-X.md`, `docs/adr/NNNN-decision.md`  
**Точка контроля** | Архитектор принимает решение, фиксирует в ADR  
**Обратный ход** | Если design нереализуем → новый ADR (supersedes) + CR  
**Latency-класс** | Фоновый  

**Правило:** RFC — переговоры, ADR — контракт. Если решение затрагивает публичные интерфейсы, сначала RFC с окном обсуждения (3 рабочих дня), затем ADR.

**Enforceable:** каждый ADR обязан содержать секцию **Invariants** — список проверяемых утверждений (запрет импортов, требования к конкурентности, контракты типов). Каждый инвариант должен быть либо (а) выражен правилом линтера, либо (б) тестом, либо (в) аннотацией в коде. ADR без enforceable-инвариантов не принимается.

### 2.4. Этап 3: Design + ADR → API-Contract

Параметр | Значение  
---|---  
**Агент** | Навык генерации OpenAPI 3.1 из design-документа  
**Контекст** | Design + ADR + текущие API-схемы (для совместимости)  
**Артефакт в Git** | `api/openapi.yaml`  
**Точка контроля** | Разработчики и потребители API проверяют контракт  
**Обратный ход** | Если контракт неполон → PR `fix/api-contract` + уведомление  
**Latency-класс** | Фоновый  

**Gitea Actions:** блокирует PR, если API-схема меняется без ссылки на ADR.

**Enforceable:** каждое изменение `openapi.yaml` обязано сопровождаться контрактным тестом (проверка схемы ответа, кодов, обязательных полей). Diff-чек: если изменён `openapi.yaml`, но не изменён код — PR блокируется; если изменён код, затрагивающий API, но не изменён `openapi.yaml` — PR блокируется.

### 2.5. Этап 4: API-Contract → Tasks

Параметр | Значение  
---|---  
**Агент** | Декомпозиция на задачи с оценкой рисков  
**Контекст** | OpenAPI + Context Provider (схема БД, зависимости, legacy)  
**Артефакт в Git** | Issues в трекере + `docs/tasks/feature-X.md`  
**Точка контроля** | Тимлид назначает приоритеты и исполнителей  
**Обратный ход** | Если задача нереализуема → Change Request в API-контракт  
**Latency-класс** | Фоновый  

**Правило трассировки:** каждая задача обязана содержать ссылку на endpoint в `openapi.yaml` и на ADR. Gitea Actions проверяет это при создании issue.

**Оценка:** агент генерирует не «часы», а **риски** («требуется миграция БД», «затрагивает legacy-сервис X»). Человек превращает это в оценку.

**Enforceable:** каждая задача обязана содержать ссылку на конкретный acceptance-критерий из specs. Задача без acceptance-критерия не проходит CI-гейт.

### 2.6. Этап 5: Tasks → Apply

Параметр | Значение  
---|---  
**Агент** | OpenHands в изолированной песочнице: код, тесты, SAST  
**Контекст** | Task + ADR + API-контракт + Context Provider  
**Артефакт в Git** | PR + Self-Check Report  
**Точка контроля** | Обязательное ревью человеком  
**Обратный ход** | Если контракт неполон → два PR: `fix/api-contract` + `feat/implementation` (blocked-by)  
**Latency-класс** | Фоновый  

**Guide Right: как формулируется задание агенту.**

Промпт-задание для Apply строится по трём правилам (в порядке возрастания рычага):

1. **Управляй структурой, а не синтаксисом.** Слабый промпт: «напиши функцию для применения скидок». Направляющий промпт: «добавь обработку скидок. Она живёт в пакете `pricing`. Не должна импортировать ничего из `order` или `billing`; зависит только от value-объекта `PricingInput`. Возвращает `Money`, никогда не примитивный `double`». Ты не описываешь код — ты описываешь **коробку**, в которую код должен поместиться. Агент исключительно хорош в заполнении коробки и исключительно плох в придумывании самой коробки.

2. **Назови инвариант — потом проси реализацию.** Слабый промпт: «сделай этот класс потокобезопасным». Направляющий промпт: «этот класс одновременно читается пулом запросов и пулом планировщика. Должен быть безопасен при конкурентных вызовах `recordHit` и `snapshot`. Используй lock-free стратегию на атомиках; не вводи `synchronized` блок». Инвариант — то, чем владеет архитектор. Реализация — то, чем владеет агент. Явное называние инварианта не даёт агенту молча обменять его на более просто выглядящее решение.

3. **Сделай границу видимой в самом коде.** Если ты третий раз печатаешь в промпте «не меняй эту сигнатуру, это публичный контракт» — инструкция должна жить в исходнике, как аннотация, которую инструментарий ИИ читает автоматически. Повторяющееся устное руководство конвертируется в постоянные code-resident signposts.

**Enforceable:** правило трёх повторений. Если ревьюер третий раз оставляет один и тот же комментарий — он обязан создать задачу на превращение этого правила в code-resident signpost (аннотацию, правило линтера, маркер для агента).

## ⚡ 3. Fast-Track: формализация исключений

### 3.1. Схема маршрутов

                             +---------------------+
                             |   Входящая задача   |
                             +----------+----------+

                        +---------------+---------------+

                        v               v               v
                +--------------+ +--------------+ +--------------+
                |  FULL CYCLE  | |  FAST-TRACK  | |   HOTFIX     |
                +--------------+ +--------------+ +--------------+
                | RFC -> ADR   | | PR + Self-   | | PR + краткий |
                | -> OpenAPI   | | Check Report | | Self-Check   |
                | -> Tasks     | |              | |              |
                | -> PR        | |              | |              |
                +--------------+ +--------------+ +--------------+

                        v               v               v
                +--------------+ +--------------+ +--------------+
                |  Большие     | | Bugfix P2/P3 | | P0/P1,       |
                |  фичи, API,  | | Dependency   | | production   |
                |  БД, security| | bump, typo,  | | down,        |
                |  >3 дней     | | refactor     | | security     |
                +--------------+ +--------------+ +--------------+

### 3.2. Маршрут A: Full Cycle

**Критерии:** затрагивает публичные API, БД, безопасность, или оценивается >3 дней работы.

**Артефакты:** RFC → ADR → OpenAPI → Tasks → PR + Self-Check Report.

### 3.3. Маршрут B: Fast-Track

**Критерии (автоматическая проверка):**

  * Bugfix P2/P3 (не hotfix).
  * Dependency bump (minor/patch).
  * Typo, docs, комментарии.
  * Рефакторинг без изменения поведения (покрыт тестами).

**Артефакты:** PR + Self-Check Report (сокращённый). **Пропускаются:** RFC, ADR, Design, OpenAPI (если API не меняется).

**Активация:** метка `fast-track` на PR. Gitea Actions проверяет критерии. Если критерии не выполнены — метка снимается, PR блокируется.

**Latency-метка:**

  * `fast-track:interactive` — для IDE-задач (2–5 сек).
  * `fast-track:background` — для PR/ревью (5–15 мин).

**Enforceable:** даже в Fast-Track сохраняются dependency rules и контрактные тесты, если затрагиваются соответствующие зоны. Fast-Track ускоряет процесс, но не отменяет физические границы.

### 3.4. Маршрут C: Hotfix

**Критерии:** P0/P1, production down, security incident.

**Артефакты:** PR + краткий Self-Check Report. Всё остальное — постфактум.

**Активация:** только владелец репозитория или on-call инженер. После инцидента — Post-Mortem с обязательным созданием RFC/ADR, если проблема системная.

## 💰 4. Compute Units: универсальная метрика

### 4.1. Формула

    1 CU = 1 GPU-час на RTX PRO 6000 (или эквивалент)

    Для API-моделей:
    1M токенов GigaChat Max = 0.65 CU

**Почему это работает:**

  * GigaChat API Max стоит 650 ₽ за 1M токенов.
  * При стоимости GPU-часа ~1000 ₽/час на RTX PRO 6000 — 1M токенов = 0.65 GPU-часа.
  * Это позволяет сравнивать on-prem и API в одной метрике.

### 4.2. Бюджеты агентов

Параметр | Фоновый | Интерактивный | При превышении  
---|---|---|---  
**Max CU** | 1.0 CU | 0.02 CU | Остановка. Diagnosis Report  
**Max iterations** | 30 | 5 | Остановка. Diagnosis Report  
**Max tokens** | 200 000 | 5 000 | Остановка. Уведомление  
**Max wall-time** | 15 минут | 5 секунд | Остановка. Лог действий  

**Пересчёт CU в рубли:** `CU_TO_RUB = 1000 ₽` (on-prem) или `650 ₽` (API).

## 🔄 6. Fallback-стратегия

### 6.1. Схема

    +-----------------------------------------------------------------------------+
    |                     УРОВЕНЬ 1: GigaChat 3.5 Ultra                           |
    |                          (On-prem, 432B MoE)                                |
    +-------------------------------------+---------------------------------------+

                  +----------------------+----------------------+
                  | error rate >5%       | latency >30s         | GPU util >90%
                  v                      v                      v
    +-----------------------------------------------------------------------------+
    |                     УРОВЕНЬ 2: GigaChat 3 Lightning                         |
    |                          (Edge / API)                                       |
    +-------------------------------------+---------------------------------------+

                  +----------------------+----------------------+
                  | error rate >10%      | latency >60s         |
                  v                      v                      v
    +-----------------------------------------------------------------------------+
    |                     УРОВЕНЬ 3: HUMAN ESCALATION                             |
    |                          (Ручное выполнение)                                |
    +-----------------------------------------------------------------------------+

### 6.2. Критерии переключения

Критерий | Порог | Действие  
---|---|---  
**Error rate** | >5% за 5 мин | Переключение на Уровень 2  
**Latency** | >30 сек (p95) | Переключение на Уровень 2  
**GPU utilization** | >90% | Переключение на Уровень 2  
**Error rate** | >10% за 5 мин | Переключение на Уровень 3  
**Latency** | >60 сек (p95) | Переключение на Уровень 3  

**Circuit Breaker:** если Уровень 1 недоступен >15 минут — circuit breaker открывается, все запросы идут на Уровень 2. Автоматически закрывается через 5 минут после восстановления.

**Правило:** Fallback — не «опция», а обязательный слой. Без него production-система не выживает.

## 🧪 7. Mutation Testing: Diff-based

### 7.1. Механика

Параметр | Значение  
---|---  
**Запуск** | Асинхронно, после слияния PR (не блокирует)  
**Область** | Только изменённые модули (по diff)  
**Mutation score** | Считается для изменённых модулей  
**Накопленный score** | Отслеживается по репозиторию отдельно  

### 7.2. Правила

  1. **Блокирующий порог:** mutation score для изменённых модулей <60% → PR помечается `test-quality-low`, требуется ручное ревью тестов.
  2. **Накопленный score:** если общий mutation score по репозиторию падает ниже 50% — создаётся задача `tech-debt:mutation-testing`.
  3. **Инструменты:** Cosmic Ray (Python), Mutmut (Python), или аналоги для других языков.

**Почему это работает:** Diff-based mutation testing не блокирует PR, но даёт точную картину качества тестов именно для нового кода. Накопленный score предотвращает незаметную деградацию.

### 7.3. Signposts: превращение повторяющихся инструкций в код

Если ревьюер третий раз оставляет один и тот же комментарий — это сигнал, что правило должно жить в коде, а не в промпте.

Типы signposts:

Тип | Пример | Кто проверяет  
---|---|---  
**Enforceable** | правило линтера, ArchUnit, dependency-cruiser | CI, автоматически  
**Инвариант** | `@Invariant("lock-free, no synchronized")` | тест + чтение агентом  
**Контракт** | `@PublicApi`, тест на сигнатуру | контрактный тест  

**Правило:** повторяющееся устное руководство → постоянный code-resident signpost. Это высший рычаг Guide Right: ты перестаёшь повторяться.

## 🔐 8. Secret Scanning: до LLM Gateway

### 8.1. Порядок действий в Gitea Actions

    1. Pre-commit hook: Gitleaks / Trufflehog (локально, у разработчика)
    2. Gitea Actions (до передачи контекста в LLM Gateway):
       - Semgrep Secrets (semgrep ci)
       - Проверка .env, config-файлов
       - Если найден секрет -> PR блокируется, уведомление security-team
    3. Только после прохождения — контекст передаётся в агент

**Почему Semgrep Secrets:** он поддерживает **валидацию** — проверяет, является ли найденный секрет активным. Это снижает false positives и позволяет приоритизировать ротацию.

**Правило:** Semgrep Secrets запускается в режиме `Block` — scan job завершается с exit code 1 при обнаружении активного секрета.

## 🔄 9. Context Enrichment

### 9.1. Механика

  1. Если ревьюер добавил контекст, которого не было у агента (например, «этот модуль deprecated, не трогай»), — это сигнал.
  2. Ревьюер ставит метку `context-gap`.
  3. Gitea Actions логирует это в Context Provider Queue.
  4. Context Provider дополняется: либо комментарий в ADR, либо запись в `docs/context/legacy-notes.md`.

**Правило:** каждый `context-gap` — это улучшение Context Provider для будущих агентов.

**Дополнение 2.2:** контекст-провайдер может использовать MCP-сервер для Gitea/Forgejo для автоматического чтения репозиториев, issues, PR. Это позволяет агенту получать свежий контекст без ручного копирования.

**Связь с Guide Right:** Context Enrichment — это постфактум-улучшение. Guide Right (§2.6) — это управление в реальном времени. Оба нужны: первый улучшает контекст для будущих задач, второй удерживает текущую генерацию в границах.

## 💵 10. Cost per Task: ключевая метрика

### 10.1. Формула

    Cost per Task (агент)  = (CU_total × CU_TO_RUB) + (часы ревью × ставка)
    Cost per Task (человек) = часы × ставка

### 10.2. Пример

Параметр | Агент | Человек  
---|---|---  
**CU_total** | 0.5 CU | —  
**CU_TO_RUB** | 1000 ₽ | —  
**Время ревью** | 0.5 часа | —  
**Ставка** | 3000 ₽/час | 3000 ₽/час  
**ИТОГО** | 0.5×1000 + 0.5×3000 = 2000 ₽ | 4×3000 = 12000 ₽  

**Вывод:** агент в 6 раз дешевле для задачи, которую он может закрыть.

**Порог окупаемости:** если `Cost per Task (агент) > 0.7 × Cost per Task (человек)` — задача слишком сложная для агента. Требуется упрощение или ручное выполнение.

**Правило:** Cost per Task отслеживается для каждого типа задач. Если метрика деградирует — это сигнал для пересмотра промптов или контекста.

## 💰 11. TCO-модель: On-Prem vs API

### 11.1. Сравнение вариантов

Вариант | CAPEX | OPEX | Когда выгоден  
---|---|---|---  
**On-prem GigaChat 3.5 Ultra** | GPU-кластер (RTX PRO 6000 / H200) | Электроэнергия, MLOps | Утилизация >60%, data residency  
**GigaChat API** | 0 | ~650 ₽/1M токенов (Max) | Пилот, переменная нагрузка, нет GPU  
**LiteLLM + Ollama (GigaChat 3 Lightning)** | Минимальный (1 GPU) | Электроэнергия | Edge-задачи, низкая latency  

### 11.2. Формула принятия решения

    Стоимость on-prem = CAPEX / (срок_амортизации × утилизация) + OPEX_месяц
    Стоимость API     = (токены_месяц / 1M) × цена_за_1M

**Порог окупаемости on-prem:** если утилизация GPU >60% и объём >500M токенов/месяц — on-prem выгоднее. Иначе — API или гибрид (база в облаке, пики через API).

**Важно:** on-prem оправдан только при высокой утилизации GPU. Экономия на токенах съедается затратами на железо и MLOps-кадры.

## 🔄 12. Обратные связи (Change Management)

### 12.1. Механика обратного хода

    +-----------------------------------------------------------------------------+
    |  Агент обнаружил несоответствие в apply                                     |
    +-------------------------------------+---------------------------------------+

                  +-----------------------+-----------------------+

                  v                                               v
    +---------------------------+              +--------------------------------+
    | PR fix/api-contract       |              | PR feat/implementation         |
    | (изменение openapi)       |              | blocked-by: #123               |
    +-------------+-------------+              +--------------------------------+

                  v
    +-----------------------------------------------------------------------------+
    |  Уведомление владельца ADR                                                  |
    |  Если принципиальное решение -> новый ADR (supersedes)                      |
    +-----------------------------------------------------------------------------+

### 12.2. Формализованные метки

Метка | Значение  
---|---  
`blocked-by: #N` | PR не может быть смёржен без PR #N  
`supersedes: ADR-NNNN` | Новый ADR заменяет старый  
`change-request` | Изменение затрагивает принятое решение  
`needs-rfc` | Требуется обсуждение до принятия  

### 12.3. Автоматизация обратного хода

**Enforceable:** если PR изменяет `openapi.yaml`, но не изменяет код — PR блокируется. Если PR изменяет код, затрагивающий API, но не изменяет `openapi.yaml` — PR блокируется. Diff-чек запускается Gitea Actions на каждый PR.

**Enforceable:** если PR помечен `change-request`, он не мержится без нового ADR или явного `supersedes`.

## 🧱 13. Enforceable-звенья: от трассировки к контролю

### 13.1. Проблема

Трассировка (§14) отвечает на вопрос «почему эта строка так написана» **после** факта. Она делает отклонение **обнаружимым**, но не **предотвращаемым**. Enforceable-звенья отвечают на вопрос «может ли агент написать иначе» **во время**.

### 13.2. Таблица enforceable-звеньев

Источник | Enforceable-форма | Где живёт | Что ловит  
---|---|---|---  
ADR (границы) | правило зависимостей | CI (ArchUnit / dependency-cruiser) | запрещённые импорты  
ADR (инварианты) | тест инварианта | test suite | нарушение конкурентности, идемпотентности  
Specs | acceptance-тесты (Given/When/Then) | test suite | несоответствие поведения  
`openapi.yaml` | контрактные тесты | CI | несоответствие схемы, кодов, полей  
Код ↔ документ | diff-чек | CI-гейт | рассинхронизация  
Повторяющиеся инструкции | code-resident signpost | исходник | потеря инварианта агентом  

### 13.3. Три уровня enforceable

**Уровень 1: Enforceable в коде (обязательно)**

  * ADR (границы) → правило линтера.
  * ADR (инварианты) → тест инварианта.
  * Specs → acceptance-тесты.
  * API-контракт → контрактные тесты.

**Уровень 2: Enforceable в CI (обязательно)**

  * PR-гейт: не мержится, пока не проходят контрактные и acceptance-тесты.
  * Проверка синхронизации: изменение `openapi.yaml` требует изменения кода, и наоборот.
  * Проверка ссылок: каждый PR ссылается на `tasks/feature-X.md`; каждая задача — на ADR и acceptance-критерий.
  * Self-Check Report как артефакт: не «агент сказал, что всё хорошо», а чек-лист с ссылками на прогоны тестов.

**Уровень 3: Enforceable в промпте (Guide Right)**

  * Агент получает коробку: пакет, зависимости, типы возврата.
  * Агент получает инварианты: что нельзя терять.
  * Повторяющиеся инструкции → signposts в коде.

### 13.4. Минимальный набор для старта

Если нужно начать с малого — три вещи дают 80% контроля:

  1. **Один линтер зависимостей** (dependency-cruiser / ArchUnit) — держит ADR-границы.
  2. **Контрактные тесты на `openapi.yaml`** — держит API-контракт.
  3. **CI-гейт на синхронизацию** — изменение кода требует изменения соответствующего документа.

Остальное — расширение по мере роста.

## 🛡️ 15. Защита от парадокса Джевонса

### 15.1. В чём риск

В 1865 году Уильям Стэнли Джевонс заметил: чем эффективнее паровые двигатели жгут уголь, тем больше угля Британия потребляет в совокупности. Эффективность снижает стоимость единицы результата → открывает новые способы применения → объём растёт быстрее, чем экономия.

В кодовой базе тот же закон: **чем дешевле писать код (в том числе с агентом), тем больше кода будет написано** — и тем важнее дисциплина, которая решает, что писать не нужно.

### 15.2. Где это бьёт по Blueprint

Blueprint подробно считает стоимость (`Cost per Task`, §10) и делает вывод «агент в 6 раз дешевле». Но нигде нет тормоза против размножения фич. Если агент дешёвый — заказывают больше фич, растёт сложность системы, и выигрыш съедается.

### 15.3. Меры

  1. **Метрика «отклонённые proposal».** В §16 (метрики успеха) добавить: доля proposal, отклонённых на этапе specs. Если она близка к нулю — фильтр не работает.
  2. **ADR фиксирует не только «что решили», но и «что решили НЕ делать».** Секция `Non-Goals` обязательна.
  3. **API-контракт ограничивает поверхность.** Чем жёстче контракт, тем меньше соблазна расширять его «за просто так».
  4. **Главная метрика — не «сколько кода написали», а «сколько кода НЕ написали».** В мире дешёвого кода ценность инженера смещается от производства к отказу от производства.

## 🎯 16. Ключевые принципы

  1. **Human-in-the-Loop** — ИИ генерирует, человек валидирует.
  2. **Docs-as-Code** — все артефакты в Git.
  3. **Обратные связи — норма** — Change Request, blocked-by, supersedes.
  4. **Fast-Track как условие выживания** — процесс без исключений = бюрократия.
  5. **Compute Units как универсальная метрика** — для on-prem и API.
  6. **Diff-based Mutation Testing** — асинхронно, только изменённые модули.
  7. **Fallback с формализованными критериями** — error rate, latency, GPU util.
  8. **Latency-классы** — фоновые vs интерактивные.
  9. **Cost per Task** — ключевая метрика для масштабирования.
  10. **Secret Scanning до LLM** — Semgrep Secrets с валидацией.
  11. **Enforceable-звенья — не опция.** Трассировка без enforcement декоративна. Каждое архитектурное решение имеет enforceable-представление в коде или CI.
  12. **Guide Right.** Управляй структурой, а не синтаксисом. Называй инвариант. Превращай повторяющиеся инструкции в code-resident signposts.
  13. **Защита от парадокса Джевонса.** Дешёвый код → больше кода. Дисциплина «что не делать» важнее скорости «что делать».

## 🚀 18. Итог

Blueprint — это **промышленная система с точными метриками**.

  * Compute Units позволяют сравнивать on-prem и API в одной метрике.
  * Diff-based Mutation Testing не блокирует PR, но отслеживает качество.
  * Fallback с критериями — обязательный слой для production.
  * Latency-классы разделяют фоновые и интерактивные задачи.
  * Cost per Task отвечает на вопрос: «Стоит ли масштабировать?»
  * **Enforceable-звенья делают отклонение от архитектуры физически невозможным, а не просто обнаружимым.**
  * **Guide Right удерживает генерацию в границах в реальном времени.**
  * **Защита от парадокса Джевонса не даёт дешёвому коду размножиться в сложность.**

Это уже не «регламент» и не «blueprint». Это **операционная система для AI-driven разработки**, которая выживает в enterprise-контуре, потому что считает деньги, latency, качество и **не даёт агенту уйти в сторону**.
