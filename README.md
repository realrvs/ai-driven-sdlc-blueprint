## 🧭 2. Принципы модернизации пайплайна

Модернизация — не добавление этапов, а **изменение природы каждого этапа**. Добавление шагов в эпоху дешёвой генерации кормит парадокс Джевонса: чем дешевле произвести шаг, тем больше бессмысленных шагов производится.

**Принципы:**

1. **«Как» бесплатно, «почему» дорого.** Каждый этап обязан производить «почему», а не только «что».
2. **Каждое «почему» имеет enforceable-носитель.** ADR, правило линтера, тест, инвариант в коде, CI-гейт.
3. **Каждый trade-off назван явно.** Если не назван — агент его нарушит, не зная.
4. **Форма важнее отдельной реализации.** Метрика — не «сколько кода», а «в какую форму он лёг».
5. **Защита от Джевонса.** Явный гейт «что решили НЕ делать» (Non-Goals).
6. **Дифференциация по маршрутам.** Full Cycle, Fast-Track, Hotfix — разная глубина применения.
7. **Метрики без целей не создают стимула накручивать.** KPI и observability разделены.

**Схема модернизированного пайплайна:**

    proposal → specs → design → adr → api-contract → tasks → apply
       │         │        │       │         │           │       │
       ▼         ▼        ▼       ▼         ▼           ▼       ▼
     Non-     AC +     Trade-  Invari-  Contract   AC-      Prompt
     Goals    Given/   offs    ants +   + diff-    link +   lineage +
              When/    matrix  Non-     check      risk     enforceable
              Then             Goals               notes    checks

Справа от каждой стрелки — **носитель «почему»** и **enforceable-форма**. Без них стрелка декоративна.

### 3.2. Этап 1: Proposal → Proposal + Non-Goals

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra (фоновый), промпт «анализ идеи → proposal»  
**Контекст** | Бизнес-ограничения, интеграции, история похожих фич  
**Артефакт в Git** | `docs/proposal/feature-X.md`  
**Точка контроля** | Аналитик проверяет черновик, дополняет контекстом  
**Обратный ход** | Если proposal неполон → новый коммит, уведомление аналитика  
**Latency-класс** | Фоновый  

**Что производит:** идея + явная секция **Non-Goals** — что мы решили **не** делать и почему.

**Почему:** защита от Джевонса. Дешёвый код → соблазн добавить всё. Non-Goals — тормоз.

**Носитель «почему»:** `docs/proposal/feature-X.md#non-goals`.

**Enforceable:** proposal без Non-Goals не принимается.

### 3.3. Этап 2: Specs → Specs + Acceptance Criteria

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra, навык генерации specs  
**Контекст** | Proposal + Non-Goals + бизнес-ограничения  
**Артефакт в Git** | `docs/specs/feature-X.md`  
**Точка контроля** | Аналитик проверяет черновик, дополняет контекстом  
**Обратный ход** | Если specs неполны → новый коммит, уведомление аналитика  
**Latency-класс** | Фоновый  

**Что производит:** поведение + **AC в Given/When/Then** + явные границы (что spec покрывает, что нет).

**Почему:** AC — это «почему» в форме, которую можно проверить. Без AC агент реализует *что-то*, но не то.

**Носитель «почему»:** `docs/specs/feature-X.md#acceptance-criteria`.

**Enforceable:** каждая AC становится acceptance-тестом на этапе Apply. Specs без AC блокируется CI.

### 3.4. Этап 3: Design → Design + Trade-off Matrix

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra, навык генерации design  
**Контекст** | Specs + текущая архитектура (из Context Provider)  
**Артефакт в Git** | `docs/design/feature-X.md`  
**Точка контроля** | Архитектор проверяет trade-offs  
**Обратный ход** | Если design нереализуем → CR в specs  
**Latency-класс** | Фоновый  

**Что производит:** архитектура + **явная матрица trade-offs** — какие характеристики конкурируют, какая побеждает, почему.

**Почему:** первый закон Ричардса-Форда. AI не взвешивает trade-offs. Если они не названы — они будут нарушены.

**Носитель «почему»:** `docs/design/feature-X.md#trade-offs`.

**Enforceable:** design без trade-off matrix не принимается. Каждый trade-off → минимум один инвариант или правило.

Пример матрицы:

| Характеристика A | Характеристика B | Что победило | Почему |
|---|---|---|---|
| Latency | Memory | Latency | Память дефицитна (см. ADR-0012) |
| Consistency | Availability | Consistency | Финансовые операции (см. ADR-0034) |

### 3.5. Этап 4: ADR → ADR + Invariants + Non-Goals

Параметр | Значение  
---|---  
**Агент** | GigaChat 3.5 Ultra, навык генерации ADR (шаблон MADR)  
**Контекст** | Design + trade-off matrix + текущая архитектура  
**Артефакт в Git** | `docs/adr/NNNN-decision.md`  
**Точка контроля** | Архитектор принимает решение, фиксирует в ADR  
**Обратный ход** | Если design нереализуем → новый ADR (supersedes) + CR  
**Latency-класс** | Фоновый  

**Что производит:** решение + альтернативы + **Invariants** (проверяемые утверждения) + **Non-Goals** (что решение явно не покрывает).

**Почему:** ADR — корень «почему». Из него растут enforceable-носители. ADR без инвариантов — декларация без последствий.

**Носитель «почему»:** `docs/adr/NNNN-decision.md#invariants`, `#non-goals`.

**Enforceable:** каждый инвариант → правило линтера, тест или аннотация в коде. ADR без enforceable-инвариантов не принимается.

Пример:

    ## Invariants
    - I-1: pricing не импортирует order или billing
    - I-2: возвращаемый тип — Money, не double
    - I-3: lock-free, без synchronized

    ## Non-Goals
    - Не покрывает multi-currency (отдельный ADR)
    - Не покрывает исторические скидки

### 3.6. Этап 5: API-Contract → Contract + Diff-Check

Параметр | Значение  
---|---  
**Агент** | Навык генерации OpenAPI 3.1 из design-документа  
**Контекст** | Design + ADR + текущие API-схемы (для совместимости)  
**Артефакт в Git** | `api/openapi.yaml`  
**Точка контроля** | Разработчики и потребители API проверяют контракт  
**Обратный ход** | Если контракт неполон → PR `fix/api-contract` + уведомление  
**Latency-класс** | Фоновый  

**Что производит:** OpenAPI + **контрактные инварианты** (что не может меняться) + **diff-чек** код ↔ контракт.

**Почему:** контракт — это граница, которую агент легко нарушит. Diff-чек делает нарушение физически невозможным.

**Носитель «почему»:** `api/openapi.yaml` + комментарии-инварианты в нём.

**Enforceable:** контрактные тесты + diff-чек (изменение контракта требует изменения кода, и наоборот).

**Gitea Actions:** блокирует PR, если API-схема меняется без ссылки на ADR.

### 3.7. Этап 6: Tasks → Tasks + AC-link + Risk Notes

Параметр | Значение  
---|---  
**Агент** | Декомпозиция на задачи с оценкой рисков  
**Контекст** | OpenAPI + Context Provider (схема БД, зависимости, legacy)  
**Артефакт в Git** | Issues в трекере + `docs/tasks/feature-X.md`  
**Точка контроля** | Тимлид назначает приоритеты и исполнителей  
**Обратный ход** | Если задача нереализуема → Change Request в API-контракт  
**Latency-класс** | Фоновый  

**Что производит:** задачи + **ссылка на конкретный AC** + **risk notes** (что может пойти не так).

**Почему:** каждая задача должна быть привязана к проверяемому критерию. Risk notes — это «почему» на уровне задачи.

**Носитель «почему»:** `docs/tasks/feature-X.md`.

**Enforceable:** задача без ссылки на AC не проходит CI-гейт.

**Оценка:** агент генерирует не «часы», а **риски** («требуется миграция БД», «затрагивает legacy-сервис X»). Человек превращает это в оценку.

### 3.8. Этап 7: Apply → Apply + Prompt Lineage + Enforceable-Checks

Параметр | Значение  
---|---  
**Агент** | OpenHands в изолированной песочнице: код, тесты, SAST  
**Контекст** | Task + ADR + API-контракт + Context Provider  
**Артефакт в Git** | PR + Self-Check Report  
**Точка контроля** | Обязательное ревью человеком  
**Обратный ход** | Если контракт неполон → два PR: `fix/api-contract` + `feat/implementation` (blocked-by)  
**Latency-класс** | Фоновый  

**Что производит:** код + **prompt lineage** (версионирование системных промптов) + **enforceable-проверки** в Self-Check Report.

**Почему:** это место, где «почему» должно жить рядом с кодом. Prompt lineage фиксирует «почему промпт такой». Enforceable-проверки доказывают, что инварианты соблюдены.

**Носитель «почему»:**
- Prompt lineage: Git-история системных промптов.
- Инварианты в коде: аннотации, комментарии-маркеры.
- Self-Check Report: секция «Enforceable-проверки».

**Guide Right: как формулируется задание агенту.**

Промпт-задание для Apply строится по трём правилам (в порядке возрастания рычага):

1. **Управляй структурой, а не синтаксисом.** Слабый промпт: «напиши функцию для применения скидок». Направляющий промпт: «добавь обработку скидок. Она живёт в пакете `pricing`. Не должна импортировать ничего из `order` или `billing`; зависит только от value-объекта `PricingInput`. Возвращает `Money`, никогда не примитивный `double`». Ты не описываешь код — ты описываешь **коробку**, в которую код должен поместиться. Агент исключительно хорош в заполнении коробки и исключительно плох в придумывании самой коробки.

2. **Назови инвариант — потом проси реализацию.** Слабый промпт: «сделай этот класс потокобезопасным». Направляющий промпт: «этот класс одновременно читается пулом запросов и пулом планировщика. Должен быть безопасен при конкурентных вызовах `recordHit` и `snapshot`. Используй lock-free стратегию на атомиках; не вводи `synchronized` блок». Инвариант — то, чем владеет архитектор. Реализация — то, чем владеет агент. Явное называние инварианта не даёт агенту молча обменять его на более просто выглядящее решение.

3. **Сделай границу видимой в самом коде.** Если ты третий раз печатаешь в промпте «не меняй эту сигнатуру, это публичный контракт» — инструкция должна жить в исходнике, как аннотация, которую инструментарий ИИ читает автоматически. Повторяющееся устное руководство конвертируется в постоянные code-resident signposts.

**Enforceable:** правило трёх повторений. Если ревьюер третий раз оставляет один и тот же комментарий — он обязан создать задачу на превращение этого правила в code-resident signpost (аннотацию, правило линтера, маркер для агента).

### 4.1. Схема маршрутов

                             +---------------------+
                             |   Входящая задача   |
                             +----------+----------+

                        +---------------+---------------+

                        v               v               v
                +--------------+ +--------------+ +--------------+
                |  FULL CYCLE  | |  FAST-TRACK  | |   HOTFIX     |
                +--------------+ +--------------+ +--------------+
                | RFC -> ADR   | | PR + Self-   | | PR + краткий |
                | -> OpenAPI   | | Check Report | | Self-Check   |
                | -> Tasks     | |              | |              |
                | -> PR        | |              | |              |
                +--------------+ +--------------+ +--------------+

                        v               v               v
                +--------------+ +--------------+ +--------------+
                |  Большие     | | Bugfix P2/P3 | | P0/P1,       |
                |  фичи, API,  | | Dependency   | | production   |
                |  БД, security| | bump, typo,  | | down,        |
                |  >3 дней     | | refactor     | | security     |
                +--------------+ +--------------+ +--------------+

### 4.2. Дифференциация по маршрутам

Модернизация применяется **дифференцированно**. Полный набор артефактов нужен не всегда — иначе процесс превращается в бюрократию для багфикса на одну строку.

| Маршрут | Что применяется | Что пропускается |
|---|---|---|
| **Full Cycle** | Non-Goals, AC, Trade-off Matrix, Invariants, Diff-Check, Prompt Lineage | — |
| **Fast-Track** | Enforceable-границы (dependency rules, контрактные тесты), если зона затронута; сокращённый Self-Check | RFC, ADR, Design, OpenAPI (если API не меняется), Trade-off Matrix, Prompt Lineage |
| **Hotfix** | Secret Scan, бюджет агента, краткий Self-Check | Всё остальное — постфактум |

**Правило:** Fast-Track ускоряет процесс, но **не отменяет физические границы**. Если зона защищена dependency rules или контрактными тестами — они срабатывают и в Fast-Track.

### 4.3. Маршрут A: Full Cycle

**Критерии:** затрагивает публичные API, БД, безопасность, или оценивается >3 дней работы.

**Артефакты:** Proposal + Non-Goals → Specs + AC → Design + Trade-off Matrix → ADR + Invariants → OpenAPI + Diff-Check → Tasks + AC-link → PR + Self-Check Report.

### 4.4. Маршрут B: Fast-Track

**Критерии (автоматическая проверка):**

  * Bugfix P2/P3 (не hotfix).
  * Dependency bump (minor/patch).
  * Typo, docs, комментарии.
  * Рефакторинг без изменения поведения (покрыт тестами).

**Артефакты:** PR + Self-Check Report (сокращённый). **Пропускаются:** RFC, ADR, Design, OpenAPI (если API не меняется), Trade-off Matrix, Prompt Lineage.

**Активация:** метка `fast-track` на PR. Gitea Actions проверяет критерии. Если критерии не выполнены — метка снимается, PR блокируется.

**Latency-метка:**

  * `fast-track:interactive` — для IDE-задач (2–5 сек).
  * `fast-track:background` — для PR/ревью (5–15 мин).

**Enforceable:** даже в Fast-Track сохраняются dependency rules и контрактные тесты, если затрагиваются соответствующие зоны.

### 4.5. Маршрут C: Hotfix

**Критерии:** P0/P1, production down, security incident.

**Артефакты:** PR + краткий Self-Check Report. Всё остальное — постфактум.

**Активация:** только владелец репозитория или on-call инженер. После инцидента — Post-Mortem с обязательным созданием RFC/ADR, если проблема системная.

## 💰 5. Compute Units: универсальная метрика

### 5.1. Формула

    1 CU = 1 GPU-час на RTX PRO 6000 (или эквивалент)

    Для API-моделей:
    1M токенов GigaChat Max = 0.65 CU

**Почему это работает:**

  * GigaChat API Max стоит 650 ₽ за 1M токенов.
  * При стоимости GPU-часа ~1000 ₽/час на RTX PRO 6000 — 1M токенов = 0.65 GPU-часа.
  * Это позволяет сравнивать on-prem и API в одной метрике.

### 5.2. Бюджеты агентов

Параметр | Фоновый | Интерактивный | При превышении  
---|---|---|---  
**Max CU** | 1.0 CU | 0.02 CU | Остановка. Diagnosis Report  
**Max iterations** | 30 | 5 | Остановка. Diagnosis Report  
**Max tokens** | 200 000 | 5 000 | Остановка. Уведомление  
**Max wall-time** | 15 минут | 5 секунд | Остановка. Лог действий  

**Пересчёт CU в рубли:** `CU_TO_RUB = 1000 ₽` (on-prem) или `650 ₽` (API).

    +-----------------------------------------------------------------------------+
    |                     УРОВЕНЬ 1: GigaChat 3.5 Ultra                           |

                  +----------------------+----------------------+

                  v                      v                      v

    +-----------------------------------------------------------------------------+

### 7.2. Критерии переключения

Критерий | Порог | Действие  
---|---|---  
**Error rate** | >5% за 5 мин | Переключение на Уровень 2  
**Latency** | >30 сек (p95) | Переключение на Уровень 2

**Правило:** Fallback — не «опция», а обязательный слой. Без него production-система не выживает.

## 🧪 8. Mutation Testing: Diff-based

### 8.1. Механика

Параметр | Значение  
---|---  
**Запуск** | Асинхронно, после слияния PR (не блокирует)  
**Область** | Только изменённые модули (по diff)  
**Mutation score** | Считается для изменённых модулей  
**Накопленный score** | Отслеживается по репозиторию отдельно  

### 8.2. Правила

  1. **Блокирующий порог:** mutation score для изменённых модулей <60% → PR помечается `test-quality-low`, требуется ручное ревью тестов.
  2. **Накопленный score:** если общий mutation score по репозиторию падает ниже 50% — создаётся задача `tech-debt:mutation-testing`.
  3. **Инструменты:** Cosmic Ray (Python), Mutmut (Python), или аналоги для других языков.

**Почему это работает:** Diff-based mutation testing не блокирует PR, но даёт точную картину качества тестов именно для нового кода. Накопленный score предотвращает незаметную деградацию.

### 8.3. Signposts: превращение повторяющихся инструкций в код

Если ревьюер третий раз оставляет один и тот же комментарий — это сигнал, что правило должно жить в коде, а не в промпте.

Типы signposts:

Тип | Пример | Кто проверяет  
---|---|---  
**Enforceable** | правило линтера, ArchUnit, dependency-cruiser | CI, автоматически  
**Инвариант** | `@Invariant("lock-free, no synchronized")` | тест + чтение агентом  
**Контракт** | `@PublicApi`, тест на сигнатуру | контрактный тест  

**Правило:** повторяющееся устное руководство → постоянный code-resident signpost. Это высший рычаг Guide Right: ты перестаёшь повторяться.

## 🔐 9. Secret Scanning: до LLM Gateway

### 9.1. Порядок действий в Gitea Actions

    1. Pre-commit hook: Gitleaks / Trufflehog (локально, у разработчика)
    2. Gitea Actions (до передачи контекста в LLM Gateway):
       - Semgrep Secrets (semgrep ci)
       - Проверка .env, config-файлов
       - Если найден секрет -> PR блокируется, уведомление security-team
    3. Только после прохождения — контекст передаётся в агент

**Почему Semgrep Secrets:** он поддерживает **валидацию** — проверяет, является ли найденный секрет активным. Это снижает false positives и позволяет приоритизировать ротацию.

**Правило:** Semgrep Secrets запускается в режиме `Block` — scan job завершается с exit code 1 при обнаружении активного секрета.

## 🔄 10. Context Enrichment

### 10.1. Механика

  1. Если ревьюер добавил контекст, которого не было у агента (например, «этот модуль deprecated, не трогай»), — это сигнал.
  2. Ревьюер ставит метку `context-gap`.
  3. Gitea Actions логирует это в Context Provider Queue.
  4. Context Provider дополняется: либо комментарий в ADR, либо запись в `docs/context/legacy-notes.md`.

**Правило:** каждый `context-gap` — это улучшение Context Provider для будущих агентов.

**Дополнение:** контекст-провайдер может использовать MCP-сервер для Gitea/Forgejo для автоматического чтения репозиториев, issues, PR.

**Связь с Guide Right:** Context Enrichment — это постфактум-улучшение. Guide Right (§3.8) — это управление в реальном времени. Оба нужны.

## 💵 11. Cost per Task: ключевая метрика

### 11.1. Формула

    Cost per Task (агент)  = (CU_total × CU_TO_RUB) + (часы ревью × ставка)
    Cost per Task (человек) = часы × ставка

### 11.2. Пример

Параметр | Агент | Человек  
---|---|---  
**CU_total** | 0.5 CU | —  
**CU_TO_RUB** | 1000 ₽ | —  
**Время ревью** | 0.5 часа | —  
**Ставка** | 3000 ₽/час | 3000 ₽/час  
**ИТОГО** | 0.5×1000 + 0.5×3000 = 2000 ₽ | 4×3000 = 12000 ₽  

**Вывод:** агент в 6 раз дешевле для задачи, которую он может закрыть.

**Порог окупаемости:** если `Cost per Task (агент) > 0.7 × Cost per Task (человек)` — задача слишком сложная для агента. Требуется упрощение или ручное выполнение.

**Правило:** Cost per Task отслеживается для каждого типа задач. Если метрика деградирует — это сигнал для пересмотра промптов или контекста.

## 💰 12. TCO-модель: On-Prem vs API

### 12.1. Сравнение вариантов

Вариант | CAPEX | OPEX | Когда выгоден  
---|---|---|---  
**On-prem GigaChat 3.5 Ultra** | GPU-кластер (RTX PRO 6000 / H200) | Электроэнергия, MLOps | Утилизация >60%, data residency  
**GigaChat API** | 0 | ~650 ₽/1M токенов (Max) | Пилот, переменная нагрузка, нет GPU  
**LiteLLM + Ollama (GigaChat 3 Lightning)** | Минимальный (1 GPU) | Электроэнергия | Edge-задачи, низкая latency  

### 12.2. Формула принятия решения

    Стоимость on-prem = CAPEX / (срок_амортизации × утилизация) + OPEX_месяц
    Стоимость API     = (токены_месяц / 1M) × цена_за_1M

**Порог окупаемости on-prem:** если утилизация GPU >60% и объём >500M токенов/месяц — on-prem выгоднее. Иначе — API или гибрид (база в облаке, пики через API).

**Важно:** on-prem оправдан только при высокой утилизации GPU. Экономия на токенах съедается затратами на железо и MLOps-кадры.

## 🧱 14. Enforceable-звенья: от трассировки к контролю

### 14.1. Проблема

Трассировка (§15) отвечает на вопрос «почему эта строка так написана» **после** факта. Она делает отклонение **обнаружимым**, но не **предотвращаемым**. Enforceable-звенья отвечают на вопрос «может ли агент написать иначе» **во время**.

### 14.2. Таблица enforceable-звеньев

Источник | Enforceable-форма | Где живёт | Что ловит  
---|---|---|---  
ADR (границы) | правило зависимостей | CI (ArchUnit / dependency-cruiser) | запрещённые импорты  
ADR (инварианты) | тест инварианта | test suite | нарушение конкурентности, идемпотентности  
Specs (AC) | acceptance-тесты (Given/When/Then) | test suite | несоответствие поведения  
`openapi.yaml` | контрактные тесты | CI | несоответствие схемы, кодов, полей  
Код ↔ документ | diff-чек | CI-гейт | рассинхронизация  
Повторяющиеся инструкции | code-resident signpost | исходник | потеря инварианта агентом  

### 14.3. Три уровня enforceable

**Уровень 1: Enforceable в коде (обязательно)**

  * ADR (границы) → правило линтера.
  * ADR (инварианты) → тест инварианта.
  * Specs → acceptance-тесты.
  * API-контракт → контрактные тесты.

**Уровень 2: Enforceable в CI (обязательно)**

  * PR-гейт: не мержится, пока не проходят контрактные и acceptance-тесты.
  * Проверка синхронизации: изменение `openapi.yaml` требует изменения кода, и наоборот.
  * Проверка ссылок: каждый PR ссылается на `tasks/feature-X.md`; каждая задача — на ADR и acceptance-критерий.
  * Self-Check Report как артефакт: не «агент сказал, что всё хорошо», а чек-лист с ссылками на прогоны тестов.

**Уровень 3: Enforceable в промпте (Guide Right)**

  * Агент получает коробку: пакет, зависимости, типы возврата.
  * Агент получает инварианты: что нельзя терять.
  * Повторяющиеся инструкции → signposts в коде.

### 14.4. Минимальный набор для старта

Если нужно начать с малого — три вещи дают 80% контроля:

  1. **Один линтер зависимостей** (dependency-cruiser / ArchUnit) — держит ADR-границы.
  2. **Контрактные тесты на `openapi.yaml`** — держит API-контракт.
  3. **CI-гейт на синхронизацию** — изменение кода требует изменения соответствующего документа.

Остальное — расширение по мере роста.

## 🛡️ 16. Защита от парадокса Джевонса

### 16.1. В чём риск

В 1865 году Уильям Стэнли Джевонс заметил: чем эффективнее паровые двигатели жгут уголь, тем больше угля Британия потребляет в совокупности. Эффективность снижает стоимость единицы результата → открывает новые способы применения → объём растёт быстрее, чем экономия.

В кодовой базе тот же закон: **чем дешевле писать код (в том числе с агентом), тем больше кода будет написано** — и тем важнее дисциплина, которая решает, что писать не нужно.

### 16.2. Где это бьёт по Blueprint

Blueprint подробно считает стоимость (`Cost per Task`, §11) и делает вывод «агент в 6 раз дешевле». Но нигде нет тормоза против размножения фич. Если агент дешёвый — заказывают больше фич, растёт сложность системы, и выигрыш съедается.

### 16.3. Меры

  1. **Non-Goals в proposal и ADR.** Явный отказ от фич и решений. Non-Goals — предохранитель против расширения scope.
  2. **ADR фиксирует не только «что решили», но и «что решили НЕ делать».** Секция `Non-Goals` обязательна.
  3. **API-контракт ограничивает поверхность.** Чем жёстче контракт, тем меньше соблазна расширять его «за просто так».
  4. **Главная метрика — не «сколько кода написали», а «сколько кода НЕ написали».** В мире дешёвого кода ценность инженера смещается от производства к отказу от производства.
  5. **Метрика «доля отклонённых proposal» — в observability, не в KPI.** См. §18.

## 🧬 17. Prompt Lineage: системные vs ситуативные промпты

### 17.1. Проблема

«Почему» на уровне генерации должно версионироваться так же, как код. Но версионировать **весь диалог** с агентом — бессмысленно и вредно: 90% промптов — одноразовый контекст.

### 17.2. Разграничение

Тип | Пример | Версионировать? | Где хранится  
---|---|---|---  
**Системный** | шаблон задания для Apply, структура промпта, правила формулировки | **Да** | `docs/prompts/` в Git  
**Ситуативный** | «поправь этот тест», «объясни этот код», уточнения | **Нет** | история Agent Platform, срок хранения — 30 дней  

### 17.3. Правила

  1. **Системные промпты версионируются** с той же строгостью, что и код. Изменение системного промпта — это изменение поведения агента, а значит, требует ревью.
  2. **Ситуативные промпты не версионируются.** Они хранятся в телеметрии Agent Platform для отладки, но не являются артефактом.
  3. **Связь с ADR:** если системный промпт кодирует архитектурное решение (например, «не используй synchronized»), он ссылается на ADR.
  4. **Связь с signposts:** если правило из промпта повторяется третий раз — оно мигрирует в код-resident signpost (§8.3).

## 📈 18. Метрики: KPI vs Observability

### 18.1. Принцип

**Метрика, ставшая KPI, перестаёт измерять то, что должна** (Закон Гудхарта). Команды начинают оптимизировать метрику, а не реальность. Поэтому метрики разделены:

  * **KPI** — то, к чему стремимся. Давление допустимо.
  * **Observability** — то, что наблюдаем без давления. Цели нет.

### 18.2. KPI (целевые)

Метрика | Цель  
---|---  
Доля PR с Self-Check Report | 100%  
Доля задач с трассировкой | 100%  
Время от proposal до apply | Сокращение на 30–40%  
Дефекты, найденные на ревью | Снижение на 20%  
Инциденты безопасности | 0 критических  
Cost per Task (агент) / Cost per Task (человек) | < 0.7  
Mutation score (изменённые модули) | > 60%  
Накопленный mutation score | > 50%  
Fallback переключения (в месяц) | < 5% запросов  
**Доля ADR с enforceable-инвариантами** | **100%**  
**Доля PR, прошедших diff-чек синхронизации** | **100%**  

### 18.3. Observability (без целей)

Метрика | Что показывает | Почему без цели  
---|---|---  
**Доля proposal, отклонённых на этапе specs** | Работает ли фильтр | KPI создаст стимул отклонять валидные proposal  
**Доля ADR с секцией Non-Goals** | Дисциплина отказа | KPI создаст стимул писать фейковые Non-Goals  
**Повторяющиеся комментарии ревьюера (топ-10)** | Где нужны signposts | KPI создаст стимул скрывать повторения  
**Среднее время жизни ситуативного промпта** | Паттерны работы с агентом | KPI создаст стимул искусственно сокращать  
**Доля Fast-Track в общем объёме** | Баланс процесса и исключений | KPI создаст стимул гнать всё в Fast-Track  

**Правило:** observability-метрики обсуждаются на ретро, но **не влияют на оценку команды**. Их цель — понимание, не контроль.

## 🚫 19. Антипаттерны модернизации

Что делать **не** стоит. Каждый антипаттерн — это способ превратить модернизацию в бюрократию или в имитацию.

### 19.1. Превращать «почему» в KPI

**Антипаттерн:** «доля ADR с Non-Goals должна быть 100%».
**Почему плохо:** команды начнут писать фейковые Non-Goals ради метрики.
**Правильно:** Non-Goals обязательны как формат (enforceable), но их **содержательность** — observability, не KPI.

### 19.2. Требовать ссылку на ADR в каждом файле

**Антипаттерн:** «каждый файл должен ссылаться на ADR, линтер проверяет».
**Почему плохо:** ADR превращается в шум, его перестают читать. Большинство файлов не имеют архитектурно значимых границ.
**Правильно:** enforceable-носители живут там, где есть **нарушаемое** решение — правило линтера, тест, инвариант в коде. Ссылка на ADR — опциональна.

### 19.3. Версионировать весь диалог с агентом

**Антипаттерн:** «prompt lineage = хранить все промпты в Git».
**Почему плохо:** 90% промптов — одноразовый контекст. Шум убивает сигнал.
**Правильно:** версионируются только **системные** промпты. Ситуативные — в телеметрии, срок хранения ограничен.

### 19.4. Добавлять этапы вместо изменения их природы

**Антипаттерн:** «добавим этап trade-off analysis между design и adr».
**Почему плохо:** каждый новый этап кормит парадокс Джевонса. Дешёвая генерация → больше шагов → больше бюрократии.
**Правильно:** trade-off matrix — часть design, а не отдельный этап. Non-Goals — часть proposal и ADR.

### 19.5. Применять Full Cycle к багфиксу

**Антипаттерн:** «все изменения проходят через proposal → specs → design → adr».
**Почему плохо:** трение убивает скорость. Команда начнёт обходить процесс.
**Правильно:** дифференциация по маршрутам (§4). Fast-Track и Hotfix — не исключение, а норма.

### 19.6. Делать ADR единственным носителем «почему»

**Антипаттерн:** «всё „почему“ — в ADR».
**Почему плохо:** агенту в момент генерации нужно «почему» рядом с кодом, а не в отдельном документе.
**Правильно:** иерархия носителей — ADR (корень), правило линтера, инвариант в коде, AC в specs, signpost.

### 19.7. Считать «сколько кода написали» метрикой успеха

**Антипаттерн:** «агент написал 10 000 строк — успех».
**Почему плохо:** это ровно парадокс Джевонса. Больше кода ≠ лучше.
**Правильно:** метрика — «сколько кода НЕ написали» и «в какую форму лёг написанный код».

## 🎯 20. Ключевые принципы

  1. **Human-in-the-Loop** — ИИ генерирует, человек валидирует.
  2. **Docs-as-Code** — все артефакты в Git.
  3. **Обратные связи — норма** — Change Request, blocked-by, supersedes.
  4. **Fast-Track как условие выживания** — процесс без исключений = бюрократия.
  5. **Compute Units как универсальная метрика** — для on-prem и API.
  6. **Diff-based Mutation Testing** — асинхронно, только изменённые модули.
  7. **Fallback с формализованными критериями** — error rate, latency, GPU util.
  8. **Latency-классы** — фоновые vs интерактивные.
  9. **Cost per Task** — ключевая метрика для масштабирования.
  10. **Secret Scanning до LLM** — Semgrep Secrets с валидацией.
  11. **Enforceable-звенья — не опция.** Трассировка без enforcement декоративна.
  12. **Guide Right.** Управляй структурой, а не синтаксисом. Называй инвариант. Превращай повторяющиеся инструкции в code-resident signposts.
  13. **Защита от парадокса Джевонса.** Non-Goals и метрика «что решили НЕ делать».
  14. **Дифференциация по маршрутам.** Full Cycle, Fast-Track, Hotfix — разная глубина.
  15. **KPI и observability разделены.** Метрики без целей не создают стимула накручивать.
  16. **Prompt Lineage — только для системных промптов.** Ситуативные не версионируются.
  17. **Не добавлять этапы, а менять их природу.** Каждый этап производит «почему» и имеет enforceable-носитель.

## 🚀 21. Итог

Blueprint — это **промышленная система с точными метриками**.

  * Compute Units позволяют сравнивать on-prem и API в одной метрике.
  * Diff-based Mutation Testing не блокирует PR, но отслеживает качество.
  * Fallback с критериями — обязательный слой для production.
  * Latency-классы разделяют фоновые и интерактивные задачи.
  * Cost per Task отвечает на вопрос: «Стоит ли масштабировать?»
  * **Enforceable-звенья делают отклонение от архитектуры физически невозможным, а не просто обнаружимым.**
  * **Guide Right удерживает генерацию в границах в реальном времени.**
  * **Защита от парадокса Джевонса не даёт дешёвому коду размножиться в сложность.**
  * **Дифференциация по маршрутам не даёт процессу превратиться в бюрократию.**
  * **KPI и observability разделены — метрики не накручиваются.**
  * **Prompt Lineage версионирует только системные промпты — без шума.**

Это уже не «регламент» и не «blueprint». Это **операционная система для AI-driven разработки**, которая выживает в enterprise-контуре, потому что считает деньги, latency, качество и **не даёт агенту уйти в сторону**.
